# Laravel / PHP / MySQL web apps (this user)

## When to Use
Trigger when the user asks to build, extend, or fix a PHP/Laravel/MySQL web application (restaurant platform, real-estate, or similar) that will run on their XAMPP and be tested locally before any deployment. Also use when setting up a fresh PHP/MySQL dev environment on a Linux VPS.

Class of work: full-stack web applications for Armand Loukou (restaurant platform, real-estate, etc.) built on Laravel + MySQL, developed on a remote Linux VPS and tested locally on the user's XAMPP before any deployment.

## Standing workflow (user preference — always)
- **Develop on the VPS, test locally on XAMPP.** The user runs XAMPP (PHP/MySQL/Apache) on their own machine. Code is written and tested on the VPS; the user copies the project into `htdocs` to test on their side. **No deployment to production until everything is validated locally.**
- **Communicate in French.** All progress reports, questions, and explanations to the user are in French.
- **Report progress step by step.** The user wants to be kept informed at each stage, not just at the end.
- **Clarify architecture decisions before coding.** The user's cahiers des charges often leave stack/scope choices open; ask via `clarify` (recommended option first) before building. For this user: Laravel monolith + MySQL + SSE (Server-Sent Events) for real-time is the accepted default on XAMPP.
- **The work runs on the VPS, not the user's machine.** If the user asks whether they can turn off their computer, reassure them: the code and DB live on the VPS; only the Hermes session is tied to the chat. Offer background/persistent execution if they want work to continue after closing the app.

## Fresh-VPS environment setup (Ubuntu)
```bash
apt-get update
apt-get install -y php8.3-cli php8.3-mbstring php8.3-xml php8.3-curl php8.3-zip \
  php8.3-mysql php8.3-sqlite3 php8.3-gd php8.3-intl php8.3-bcmath php8.3-redis \
  mariadb-server mariadb-client unzip git
# Composer (as root)
export COMPOSER_ALLOW_SUPERUSER=1
curl -sS https://getcomposer.org/installer -o /tmp/composer-setup.php
php /tmp/composer-setup.php --install-dir=/usr/local/bin --filename=composer
# Start MariaDB, create app DB + user
service mariadb start
mysql -e "CREATE DATABASE IF NOT EXISTS <db> CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci; \
  CREATE USER IF NOT EXISTS '<user>'@'localhost' IDENTIFIED BY '<pw>'; \
  GRANT ALL PRIVILEGES ON <db>.* TO '<user>'@'localhost'; FLUSH PRIVILEGES;"
# Scaffold Laravel
composer create-project laravel/laravel <project> --no-interaction
```
Then point `.env` at MySQL (DB_CONNECTION=mysql, DB_HOST=127.0.0.1, DB_DATABASE/USERNAME/PASSWORD) and run `php artisan migrate --force` to confirm the connection before building anything.

## XAMPP PHP version compatibility (critical)
- **The user's XAMPP runs PHP 8.2.12 — Laravel 13 requires PHP 8.3.** `composer install` on a Laravel 13 project fails on their machine with `Your lock file does not contain a compatible set of packages. Please run composer update.` (root composer.json `php: ^8.3` + laravel/framework locked to a 8.3-only version). This is a hard blocker, not a warning.
- **Do NOT tell the user to replace XAMPP's PHP to fix it.** They tried installing PHP 8.3.35 into XAMPP and Apache refused to start (`Apache shutdown unexpectedly`) because the bundled Apache modules/extensions are compiled for the exact bundled PHP version. The safe path is to keep their working PHP 8.2 and **deliver a Laravel 12 version of the app** instead. (If they do replace PHP, keep a `php_backup` folder and restore by renaming back — but prefer adapting the project.)
- **To build a PHP-8.2-compatible deliverable: scaffold `laravel/laravel:^12.0`** (Laravel 12 supports `php: ^8.2`), copy the app code over, and force Composer to resolve for the target PHP by adding `"config": { "platform": { "php": "8.2.12" } }` to `composer.json`, then `composer update`. This makes the lock file installable on the user's 8.2 even though the dev VPS runs 8.3. Verify with `php artisan test` (all green) and curl each page → 200 before packaging.
- **When the deliverable changes materially (e.g. PHP version), use a DIFFERENT archive filename** (`resto-platform-php82-xampp.tar.gz` vs the 8.3 one) and explicitly say "use ONLY this one, ignore the other". Reusing the same name across a version change re-creates the 'which file do I extract?' confusion.
- **XAMPP setup traps that block `composer install` / `key:generate` on the user's machine:**
  - **`;extension=zip` disabled in `C:\xampp\php\php.ini` breaks `composer install`.** Composer downloads packages as zips and needs the PHP `zip` extension (or unzip/7z on PATH) to unpack them; with it disabled it fails with `The zip extension and unzip/7z commands are both missing` and `Source fallback is disabled`. Fix: uncomment `extension=zip` in php.ini, save, reopen the terminal.
  - **Missing `.env` breaks `php artisan key:generate`.** `key:generate` reads `.env` to write the key into it; if the user replaced the project folder and never ran `copy .env.example .env`, it throws `file_get_contents(...\.env): Failed to open stream`. The install sequence must include `copy .env.example .env` BEFORE `key:generate`.
  - **Replacing the project folder drops `vendor/`** (it is excluded from the archive), so the user must re-run `composer install` in the new folder or Laravel fails with `Failed opening required '...\vendor/autoload.php'`. Always restate the full sequence after a re-extract: `composer install` → `copy .env.example .env` → `php artisan key:generate` → `php artisan migrate --seed` → `php artisan serve`.

## Laravel 13 gotchas
- **Laravel 13 uses PHP attributes, not properties.** `#[Fillable([...])]` and `#[Hidden([...])]` on the model class replace `$fillable` / `$hidden`. Do not add `protected $fillable` expecting it to work — use the attributes. (Laravel 12 and earlier use the classic properties.)
- **When porting code from Laravel 13 down to Laravel 12, rewrite attribute-based models to classic properties.** A `User` model with `#[Fillable([...])]`/`#[Hidden([...])]` throws `MassAssignmentException: Add [establishment_id] to fillable property` on Laravel 12 because the attributes are ignored there. Replace with `protected $fillable = [...]` + `protected $hidden = [...]` (keep `casts()`). Grep for `#[Fillable`/`#[Hidden` when downgrading.
- `php artisan migrate --force` is needed when not in local env; `migrate:fresh --seed --force` resets and reseeds cleanly.
- **Laravel 13 has no `app/Http/Middleware/VerifyCsrfToken.php`.** Middleware config lives in `bootstrap/app.php` via `->withMiddleware(function (Middleware $middleware) { ... })`. To exempt public routes (a QR-code client app with no session) from CSRF, call `$middleware->validateCsrfTokens(except: ['m/*/order'])` there. Without this, a public POST returns 419 "Page Expired" because there is no session token to match.
- **Public client routes need no CSRF token in the view** once exempted — the client JS posts JSON without `X-CSRF-TOKEN`. Keep the exemption pattern narrow (`m/*/order`), not a blanket `*`.
- **Blade `@json()` cannot compile a multi-line arrow function.** `@json($products->map(fn ($p) => [ ... ]))` throws `Unclosed '[' on line N does not match ')'` at view compile time. Build the payload in the controller with `->map(...)->values()->toJson()` into a `$jsonVar`, then inject with `{!! $jsonVar !!}` (un-escaped echo) — not `@json`.
- **Blade treats a raw array from a service differently from a Collection.** If you pass `$array` (from a PHP `return [...]`) to a view, `$array->isEmpty()` fails — call `empty($array)` instead; reserve `->isEmpty()` / `->get()` for real Collections. Decide the shape in the controller and use the matching Blade test.

## Eloquent & validation pitfalls
- **Specify the FK column on every relation whose column name is not `<model>_id`.** Eloquent infers the foreign key from the related model name, so a `product_option_choices` table with column `option_id` (not `product_option_id`) breaks BOTH directions: `belongsTo(ProductOption::class)` and `hasMany(ProductOptionChoice::class)` both query `product_option_choices.product_option_id` and throw `SQLSTATE[42S22] Column not found`. Fix both sides: `belongsTo(ProductOption::class, 'option_id')` and `hasMany(ProductOptionChoice::class, 'option_id')`. Symptom: a page 500s only when the relation is eager-loaded (e.g. `with('options.choices')`), while other pages work.
- **A `nullable` validation rule does NOT put the key in `$data`.** After `$request->validate(['table_id' => 'nullable|exists:...'])`, `$data['table_id']` throws `Undefined array key` when the client omits it (e.g. counter sale with no table). Guard with `! empty($data['table_id'])` for the branch and `$data['table_id'] ?? null` for the insert. Symptom: 500 only on the no-value path, works when the field is present.
- **Delete the scaffold `tests/Feature/ExampleTest.php`** when the app redirects `/` to login — it asserts 200 on `/` and fails with 302, polluting the suite. Remove it and keep only real feature tests.
- **Recalculate order totals on EVERY creation path, not just the main POS one.** A client/QR order controller that inserts items but never recomputes `subtotal`/`total` leaves them at 0 — which silently breaks downstream logic (loyalty points = `floor(total/1000)`, reports). After inserting items, `$order->load('items')` then `$order->update(['subtotal' => $sum, 'total' => $sum])`. Symptom: order shows `total=0` in DB while items exist.
- **Eloquent `time` columns are strings, not Carbon.** A `time` column (e.g. `start_time` on a price rule) is returned as a plain string; calling `$rule->start_time->format('H:i')` throws `Call to a member function format() on string`. Compare with `substr($rule->start_time, 0, 5)` against `$at->format('H:i')`. Only `datetime`/`timestamp` casts become Carbon.
- **`whereDoesntHave('relation')` requires the relation to be defined on the model.** A query like `Order::whereDoesntHave('delivery')` throws `Call to undefined method ... delivery()` unless you add the `hasOne(Delivery::class)` relation to Order. Define the relation first, then the constraint works.
- **After every `patch` on a PHP file, run `php -l` on it.** The fuzzy patch matcher repeatedly produced corrupted output this session (`'us' => 'occupied'`, `'productsproducts'`, `'customer_phoneer_phone'`, `'ions', 'anomalies'`, `'total' 'total'`, `'m/*/order',er'`) — a duplicated/merged token that only a syntax check catches. When a patch keeps corrupting the same line, stop patching and rewrite the whole file with `write_file` instead of fighting the matcher.

## Security & access control (multi-tenant)
- **Scope cross-entity lookups to the tenant, not just the parent check.** `abort_unless($order->establishment_id === $est->id, 403)` protects the order, but a subsequent `Product::findOrFail($product_id)` from user input lets a caller in tenant A reference a product from tenant B by guessing its id. Scope the lookup: `Product::where('id', $id)->where('establishment_id', $order->establishment_id)->firstOrFail()` (404) or skip silently in a public client path (ignore foreign-tenant items). Grep controllers for `Model::find`/`findOrFail` on user-controlled ids that feed other tenants' rows.
- **Sensitive actions (annullation, remise, tiroir) require a PIN; verify constant-time.** The cahier des charges mandates a PIN for cancel/discount regardless of role; a gérant/propriétaire is exempt. Check with `hash_equals((string)$user->pin, (string)$pin)` (avoids timing side-channels) and `abort(403)` otherwise. Render `403` not just the transaction — the audit log then only records authorized actions.
- **Rate-limit the login POST route** to stop brute force: `->middleware('throttle:5,1')` on the login route (5 attempts/min). Laravel covers login CSRF, but not throttling, by default.
- **Enforce RBAC at the ROUTE level, not just in the sidebar.** Hiding a link in the sidebar is cosmetic; a user can still hit the URL directly. Protect back-office routes (menu, rapports, stock, intelligence, copilote, expansion, consolidation) with a role middleware so a serveur/caissier/cuisinier gets 403 on them. Pattern: create `app/Http/Middleware/EnsureRole.php` that `abort(403)` unless `in_array($user->role, $roles)`, register the alias in `bootstrap/app.php` via `$middleware->alias(['role' => EnsureRole::class])`, then wrap the back-office group with `Route::middleware('role:manager,owner')->group(...)`. Verify with curl per role: serveur → 403 on `/expansion`, gérant → 200.
- **Make the sidebar render per-role too** (defense in depth + UX): wrap each nav link in `@if(in_array($role, ['manager','owner']))` etc., computing `$role = auth()->user()->role` once at the top of the nav. A serveur should see only dashboard + plan de salle; a gérant sees everything. Grep the rendered HTML for the link text to confirm the right set appears per role.
- **Super-admin SaaS console: a `superadmin` role with `establishment_id = null`.** When the user asks for a console that creates/paramètres each establishment and its agents, add a `superadmin` role (seeded with no establishment), a `/admin` route group wrapped in `role:superadmin`, and a `SuperAdminController` that CRUDs establishments (name, legal_name, pays, devise, NCC, phone, address, logo upload) and creates agent accounts (manager/cashier/server/kitchen/bar/stock) scoped to a chosen establishment. Redirect `superadmin` login to `/admin` in `homeFor()`. Verify: superadmin → 200 on `/admin`, a gérant → 403.
- **When adding a `superadmin` role, include it in `isManager()`** (or any role-allowlist that gates back-office pages). A superadmin with `establishment_id = null` who is NOT in `isManager()` gets locked out of the very pages the console manages. `isManager()` should be `in_array($role, ['owner','manager','superadmin'])`.
- **Never create a user by hand in phpMyAdmin with a plaintext password — Laravel's `hashed` cast then throws `This password does not use the Bcrypt algorithm` (500 on login).** The `password` column must hold a Bcrypt hash; a raw `password` string makes `Auth::attempt` crash in `BcryptHasher`. Two reliable fixes: (a) ship a dedicated artisan command `php artisan superadmin:create` that does `User::create([... 'password' => $pw ...])` — the model's `hashed` cast hashes it automatically — and (b) if the user already inserted a bad row, run `php artisan tinker` and `$u->password = bcrypt('password'); $u->save();`. Prefer the artisan command over telling the user to paste a hash into phpMyAdmin (they will paste the raw string). Verify the stored value starts with `$2y$` and that login redirects to `/admin`.
- **Per-establishment ticket branding: the receipt already reads `$est->logo_path`.** The `Establishment` model has `logo_path` from the start; the superadmin console uploads it (`$request->file('logo')->store('logos','public')` + `php artisan storage:link`), and the receipt view renders it (`@if($est->logo_path) <img src="{{ asset('storage/'.$est->logo_path) }}">`) above the legal name. Each establishment's ticket then shows its own logo + name + NCC + currency symbol.
- **A no-auth public route must be CSRF-exempt from the start or you get 419.** Covered above under `bootstrap/app.php`. Verify `.env` → 404 and `storage/logs/*` → 403 from the web root after routing (public assets are served, dotfiles and logs are not).

## Responsive / mobile (XAMPP frontend)
- **Sidebar fixed-left breaks on small screens — make it a mobile overlay.** A `w-60` statically-positioned sidebar eats the whole viewport on a phone. Give it `fixed inset-y-0 left-0 -translate-x-full lg:translate-x-0 lg:static`, bind the transform to an Alpine store (`$store.sidebar.open ? 'translate-x-0' : '-translate-x-full'`), add a hamburger (topbar, `lg:hidden`) calling `toggle()`, a dark overlay that closes on click, and `@click="$store.sidebar.close()"` on every nav link. `lg:static` + `lg:!transform-none` restores desktop.
- **Catch Blade compile errors without a browser:** `php artisan view:cache` compiles every template and fails fast on a `<-- unclosed -->` or `@json` misuse; `php artisan view:clear` afterwards when iterating.

## Testing & packaging
- **Keep tests on SQLite `:memory:`** (default in `phpunit.xml`) so `RefreshDatabase` never wipes the dev MySQL DB. Write feature tests that exercise the full order flow (create → add item → send → pay → cancel-with-audit) plus a cross-establishment 403 isolation test.
- **Package for XAMPP as a ZIP, not tar.gz** — this user could not decompress the `.tar.gz` on Windows ("le fichier compressé n'est pas bon, je n'arrive pas à le décompresser"). A `.zip` extracts with a plain right-click → "Extraire tout…". Exclude `vendor`, `.git`, `.env`, and log files (the user runs `composer install` on their side). Verify the archive contains `artisan`, `composer.json`, `.env.example`, `INSTALL_XAMPP.md` and contains NO real `.env` or `vendor/` before handing it over. Confirm the zip is valid with `unzip -t file.zip`.
- **Before telling the user a file is ready to download, confirm it exists on disk** (`ls -lh`). A deliverable generated in an earlier session (e.g. the Word install guide) can be lost, and the user reports "je n'arrive pas à télécharger le fichier" — the real cause is the file is gone, not the download. Regenerate it, then give the path.
- **Reuse the SAME archive filename on every delivery, and tell the user to use only the latest.** The archive is regenerated after each lot under the same name; the user may download several copies and end up unsure which to extract. When handing it over, explicitly say "use ONLY this one, ignore earlier downloads" — and offer to deliver a Word `.docx` install guide.
- **When this user asks for the install steps "dans un fichier", deliver a Word `.docx`**, not a plain chat recap. Build it with the `docx` skill (`docx_create.py spec.json out.docx`): idempotent JSON spec with `blocks`, and only custom styles must be declared (built-ins like `Title`/`Heading 1`/`Normal` already exist — declaring them throws ``ValueError: document already contains style``). Structure it as: what was received / prerequisites / numbered install steps with the exact commands / demo accounts table / troubleshooting table.
- **If `docx_create.py` keeps crashing on a built-in style collision, build the docx directly with python-docx instead of fighting the spec.** The create script re-declares `Title`/`Heading 1` and throws `ValueError: document already contains style 'Title'` even after you remove them from the spec (the default template already defines them). The reliable fallback is a small standalone python-docx script that uses ONLY native styles — `doc.add_heading(text, level=N)` for headings, `doc.add_paragraph(style='List Bullet')` for bullets, `doc.add_table(style='Table Grid')` for tables — and never calls `add_style`. This produces a valid, Word-openable file with zero style collisions. Verify with `docx_validate.py` → `{"ok": true}` and `docx_read.py --text` showing the expected headings.
- **Verify authenticated HTTP pages with curl when no browser is reachable (internal/private address blocked).** Extract the session CSRF token — `curl -c cookies.txt URL | grep -oP 'name="_token" value="\K[^"]+'` — then POST login with it, keep `-b/-c cookies.txt`, and re-extract a fresh token per page. Confirm `HTTP 200` plus absence of `exception|Error` markers in the body; target 403/404 where the security tests expect them. This validates rendering and RBAC without a GUI.

## Seeding pitfalls
- **A seeder that fails partway leaves partial data** (e.g. an establishment created but users/products not). Re-running `db:seed` then hits unique-constraint violations on already-inserted rows. Recovery: fix the seeder, then `php artisan migrate:fresh --seed --force` for a clean state.
- **Validate FK references in seed data against the actual seeded values.** A category referenced as `'Plat'` (singular) while the seeded list uses `'Plats'` (plural) silently produces a null FK and a crash at the product-insert line. Cross-check every lookup key in the seed arrays against the exact strings used to create the parent rows.
- When a seeder crashes, read the full exception (not just the tail) — the failing line and SQL reveal whether it's a duplicate-key (partial seed) or a null-FK (bad reference) so you fix the right thing.
- **Use DETERMINISTIC tokens for any value that appears in a user-facing URL (QR codes, share links).** `Str::random(24)` regenerates a different token on every `migrate --seed`, so a QR URL you documented (`/m/<token>`) 404s as soon as the user re-seeds their DB. Derive the token from the row instead (`'table-' . strtolower($name)` → `table-t1`), so it is stable and predictable across reseeds. Also surface the link IN the app UI (e.g. a "Menu client" button in the floor order modal that sets `href='/m/'+qrToken`) so the user never has to type a URL by hand.
Render the QR code as an image server-side with the **official `endroid/qr-code` package v6** — a hand-rolled GD "QR" that just draws finder/sync/data patterns produces an image that LOOKS like a QR but is NOT scannable (users report "le QR s'affiche mais n'est pas scannable"). Install `composer require endroid/qr-code` (endroid v6 has an IMMUTABLE API: `new QrCode(data: $text, encoding: new Encoding('UTF-8'), errorCorrectionLevel: ErrorCorrectionLevel::High, size: $size, margin: 20, foregroundColor: new Color(0,0,0), backgroundColor: new Color(255,255,255))` + `PngWriter`; there is NO `set*`/Builder `create()` — those are v5/v4 APIs). The **marge blanche (`margin`, ≥ 15px) is MANDATORY** for phone readers. Build it server-side with a `QrCodeService` (`use Endroid\QrCode\...`) that returns PNG bytes, expose `GET /qr/{token}` as `image/png`, and `<img src="{{ route('qr.image', $table->qr_token) }}">` on each table card + a larger one in the order modal. Verify the SERVED PNG is a real scannable QR: `curl -o qr.png -w "%{content_type}"` → `image/png`, `file qr.png` → `PNG image data`, and confirm the scan of the ACTUAL URL (`/m/{token}`) with a phone. A QR that depends on a JS CDN library is useless on the same offline phone that scans it.

## Real-time on XAMPP
- Use **SSE (Server-Sent Events)** for salle→cuisine sync: works on plain Apache/PHP with no extra daemon, unlike WebSocket. Store events in a table and have the SSE endpoint poll it.
- **An infinite SSE loop blocks the mono-threaded `php artisan serve`.** `php artisan serve` handles ONE request at a time; a `while(true){ ...; sleep(1); }` SSE stream holds the single worker, so every other request (encaisser, add item, page load) queues behind it — the whole app feels slow. Fixes, in combination:
  - **Cap each SSE connection's lifetime** (e.g. break after 3s) and let the client's `EventSource` auto-reconnect — no events are lost because the client reconnects with `Last-Event-ID`.
  - **Do not replay the whole event history on first connect.** The client sends `Last-Event-ID` in a header (not a query param) on reconnect, but on the FIRST connect it sends nothing → `last_id=0` replays every historical event. Filter the query by recency (`where('created_at', '>=', now()->subSeconds(30))`) so a fresh page only sees recent events. Symptom of replay: the page reloads repeatedly right after load.
  - **Guard `location.reload()` on SSE events so it never fires while a modal is open.** If the floor page reloads on every `order.sent`/`table.status`, the order-taking modal opens then instantly disappears. Wrap the reload: `if (modal && !modal.classList.contains('hidden')) return; location.reload();`.
- Frontend stack that needs no Node build (runs directly in XAMPP htdocs): **Tailwind CSS via CDN + Alpine.js**. Avoid Vite/Next.js for the user's XAMPP-deployed apps.
- **The PUBLIC client menu (QR app scanned by phones) must be fully offline-capable — no CDN at all.** Tailwind-via-CDN + Alpine.js is fine for the back-office (the gérant's machine has internet), but a customer's phone may have no data. Alpine's `@click` and `x-show` silently do nothing when the CDN script fails to load → "nothing is clickable" and category filters don't work. For any page a customer opens (the `/m/{token}` menu), write it in **pure JS (`addEventListener`/`onclick`) + inline `<style>` CSS** with zero external `<script src>`/`<link>` — it must render and be interactive with no network. Verify by grepping the rendered HTML for `cdn.`/`alpinejs` (must be absent) and counting `onclick=` handlers. Keep the CDN stack only for authenticated back-office pages.

## Auth & performance (user-visible)
- **Redirect after login by ROLE, not `intended()`.** `redirect()->intended($home)` returns the user to whatever URL they requested before login — often `/dashboard` — so a serveur lands on the gérant dashboard. Redirect to `homeFor($role)` (serveur→`/floor`, caissier→`/pos`, cuisinier→`/kds`, gérant→`/dashboard`), honoring `session('url.intended')` only when it is an explicit internal URL that is not `/login`. Verify each role's redirect with curl (`-w "%{http_code} -> %{redirect_url}"`).
- **Consolidate N sequential HTTP calls into ONE endpoint for the POS.** A counter sale that does create-order + one request per item + pay = 3–4 round-trips, each waiting on the (mono-threaded) server → the encaissement window and confirmation feel slow. Add a single `POST /pos/quick-sale` that creates the order, inserts all items, records payments, marks paid, destocks, and updates the table inside one `DB::transaction`, and have the frontend call it once. Measure with `time curl ...` to prove the improvement (ms vs seconds).
